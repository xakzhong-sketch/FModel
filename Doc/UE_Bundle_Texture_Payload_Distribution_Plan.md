# UE Bundle Texture Payload Distribution Plan

## Goal

Add an optional, distributable texture payload workflow for cooked material bundles.

Current bundles contain texture references and cooked texture metadata, but not Unity-ready texture image files. That is correct for lightweight shader analysis, but it blocks downstream users who receive a bundle without access to the original cooked game data.

This plan keeps the default bundle lightweight and adds an explicit payload mode:

```text
Default bundle:
  shader data + material parameters + texture references + cooked texture metadata
  no decoded texture image payload

Optional texture payload:
  decoded Unity-importable texture files + sidecar metadata + manifest
  generated by the machine that has access to original UE cooked game data
```

## Problem

`source/textures/*.cooked.json` is not a texture image payload. It is metadata exported from cooked texture assets and is useful for semantic analysis only.

When material restore reports `MissingTextureGuids`, there are two possible recovery paths:

```text
1. Original game data is available:
   use ExportMissingTextures to decode missing textures from cooked paks/containers.

2. Original game data is not available:
   use a pre-exported bundle texture payload, if the bundle was distributed with one.
```

Without either source, a downstream Agent cannot recreate missing Unity texture assets from the bundle alone.

## Design Principles

1. Do not put decoded images under `source/textures`; keep that directory metadata-only.
2. Do not include image payload by default; it is an explicit size/copyright-sensitive export choice.
3. Payload files must use relative paths and machine-portable manifests.
4. Payload generation requires original UE cooked game data.
5. Payload consumption must not require original UE cooked game data.
6. Material restore DryRun remains the gatekeeper; texture import/copy happens only when `ExportMissingTextures` or the new payload import step is explicit.
7. Shader reconstruction goals must not export or import textures.

## First-Step Export Goal Choice

After this feature is implemented, the first material export step has two explicit Goal choices.

### Option A: Lightweight Bundle Export

Use the existing export Goal:

```text
/goal <FModelRepo>/Doc/UE_Cooked_Material_Bundle_Export_Goal.md current directory export <MaterialName> material
```

Output:

```text
<Bundle>/
  shader data
  material parameters
  layer/blend analysis
  texture references
  source/textures/*.cooked.json metadata
```

This does not include Unity-importable decoded texture images. Use this when the downstream workspace has access to original cooked game data, or when texture recovery is not needed yet.

### Option B: Bundle Export With Texture Payload

Add a new export Goal:

```text
/goal <FModelRepo>/Doc/UE_Cooked_Material_Bundle_With_TexturePayload_Export_Goal.md current directory export <MaterialName> material
```

Output:

```text
<Bundle>/
  all lightweight bundle files
  texture_payload/manifest.json
  texture_payload/Game/.../T_Name.png
  texture_payload/Game/.../T_Name.png.ue_texture_export.json
```

Use this when one machine will centrally export bundles and distribute them to other users or Agents that may not have original UE cooked game data.

Until the new Goal and CLI mode are implemented, Option A is the only available export Goal. Option B is the target workflow described by this plan.

## Proposed Bundle Layout

Single bundle with embedded payload:

```text
<Bundle>/
  texture_payload/
    manifest.json
    Game/Art/.../T_Name.png
    Game/Art/.../T_Name.png.ue_texture_export.json
```

Optional adjacent payload pack for large batches:

```text
<Bundle>.texture_payload/
  manifest.json
  Game/Art/.../T_Name.png
  Game/Art/.../T_Name.png.ue_texture_export.json
```

The embedded form is preferred for handoff simplicity. The adjacent form can be added later for batch size management.

## Payload Manifest

Write:

```text
texture_payload/manifest.json
```

Schema:

```json
{
  "Schema": "ue-bundle-texture-payload/v1",
  "PayloadMode": "referenced_textures",
  "GeneratedAtUtc": "...",
  "BundleName": "MI_Name.bundle",
  "Material": "/Game/...",
  "SourceGame": "Subnautica2",
  "OriginalCookedDataRequiredToRegenerate": true,
  "ImagesAreUnityImportable": true,
  "Items": [
    {
      "TextureName": "T_Name",
      "ObjectPath": "/Game/.../T_Name.0",
      "PayloadPath": "texture_payload/Game/.../T_Name.png",
      "SidecarPath": "texture_payload/Game/.../T_Name.png.ue_texture_export.json",
      "ImportIntent": "BaseColorOrBCM",
      "ColorSpace": "sRGB",
      "Width": 2048,
      "Height": 2048,
      "ByteLength": 1234567,
      "Sha256": "...",
      "ReferencedByProperties": [
        {
          "Property": "_Layer0_BCM_BaseColor_Metallic_Map",
          "StableKey": "LayerParameter:0:BCM BaseColor|Metallic Map"
        }
      ]
    }
  ],
  "Missing": [],
  "Warnings": []
}
```

All paths in the manifest must be bundle-relative. Do not write machine-local drive-rooted paths.

## Export Scopes

Support two scopes:

```text
referenced_textures
  Export every unique texture referenced by the bundle.
  Best for bundle distribution, because downstream Unity projects may be missing any of them.

missing_from_restore_report
  Export only textures listed in a material restore DryRun report.
  Best for local incremental recovery when a specific Unity project is already known.
```

The default for a distributable payload should be `referenced_textures`.

## CLI Additions

Add one new mode:

```powershell
dotnet run --project <FModelRepo>\CUE4Parse\CUE4Parse.ShaderBundleExporter\CUE4Parse.ShaderBundleExporter.csproj -c Release -- `
  --export-bundle-texture-payload `
  --game "<GameName>" `
  --paks "<GamePaks>" `
  --mapping "<GameMapping.usmap>" `
  --bundle "<Bundle>" `
  --payload-scope referenced_textures
```

Optional:

```text
--payload-out <relative-or-absolute-output>
--payload-scope referenced_textures | missing_from_restore_report
--restore-report <DryRunReport.json>
--overwrite-textures
```

Rules:

```text
1. referenced_textures reads bundle parameter and layer binding files.
2. missing_from_restore_report reads MissingTextureExportCandidates.
3. The exporter decodes textures from mounted original game data.
4. The exporter writes payload files and manifest only.
5. The exporter never modifies Unity .mat files.
6. Existing payload files are skipped unless --overwrite-textures is explicit.
```

## Restore Workflow Changes

Update `UE_Unity_Material_Property_Restore_Goal.md` so missing texture recovery source order is:

```text
1. Existing Unity project texture assets with .meta GUIDs.
2. Bundle texture_payload, if texture_payload/manifest.json exists.
3. Original UE cooked game data through ExportMissingTextures, if source paks/mapping are available.
4. Stop with an actionable blocker.
```

When payload exists and DryRun reports `MissingTextureGuids`, the Agent should:

```text
1. Read texture_payload/manifest.json.
2. Copy only required payload textures into the Unity Assets tree.
3. Preserve relative UE hierarchy under the chosen Unity output folder.
4. Copy sidecar JSON files with the images.
5. Let Unity import and generate .meta files.
6. Re-run DryRun.
7. Apply only after explicit Apply.
```

Suggested command shape for a future helper:

```powershell
python <FModelRepo>\CUE4Parse\CUE4Parse.ShaderBundleExporter\Tools\import_bundle_texture_payload.py `
  --bundle "<Bundle>" `
  --restore-report "<DryRunReport.json>" `
  --unity-assets-root "<UnityProject>/Assets" `
  --texture-out "Assets/Art/Recovered/Subnautica2"
```

The first implementation can be C# or Python. Python is simpler for copying payload files; C# is already used for decoding from cooked data.

## Bundle Agent Docs

Generated bundle docs should clearly state:

```text
This bundle may or may not include decoded texture payload files.

source/textures/*.cooked.json:
  cooked texture metadata only; not Unity-importable texture images.

texture_payload/manifest.json:
  optional decoded texture payload for downstream Unity import.

If texture_payload exists:
  use it before asking for original game paks.

If texture_payload does not exist and original game data is unavailable:
  report that missing Unity textures cannot be recovered from this bundle alone.
```

## Verifier Changes

`--verify-only` should not require payload by default.

If payload exists, verifier should validate:

```text
1. texture_payload/manifest.json is parseable.
2. Manifest schema is supported.
3. Every listed PayloadPath exists.
4. Every listed SidecarPath exists when declared.
5. Payload paths are relative and stay inside the payload directory.
6. Manifest and sidecars do not contain machine-local absolute paths.
7. Sha256 matches when present.
```

## Batch Export

For batch distribution, support:

```text
--include-texture-payload
--payload-scope referenced_textures
```

Batch behavior:

```text
1. Each bundle gets its own embedded texture_payload by default.
2. Future optimization may deduplicate into a batch-root shared texture_payload.
3. Do not deduplicate in the first version; correctness and handoff simplicity matter more.
```

## Relationship To Existing ExportMissingTextures

Keep the existing restore-stage `ExportMissingTextures` workflow.

Use cases:

```text
ExportMissingTextures:
  Local project has original game data and needs only currently missing Unity textures.

Bundle texture payload:
  Central exporter has original game data and wants to distribute self-contained recovery assets to other users/Agents.
```

They should share decoding and sidecar-writing code where practical.

## Safety Rules

```text
Do not generate texture payload unless explicitly requested.
Do not treat payload as proof of shader semantics; it is asset data plus import intent.
Do not overwrite Unity assets unless explicitly requested.
Do not write Unity .meta files in the first implementation.
Do not run payload import from PROMPT_NEXT_SESSION.md.
Do not scan or copy unrelated payload textures; use the restore report to select needed files.
Do not require original game data when consuming an existing payload.
```

## Implementation Phases

### Phase 1: Contract And Docs

```text
1. Add this plan and tasks.
2. Update material restore goal with payload source order.
3. Update generated bundle docs to explain source/textures vs texture_payload.
4. Add a new first-step Goal document for bundle export with texture payload.
5. Update one-click goals to use payload only in material restore stage.
```

### Phase 2: Payload Exporter

```text
1. Add --export-bundle-texture-payload mode.
2. Reuse MissingUnityTextureExporter decoding where possible.
3. Gather referenced textures from material_layer_parameter_bindings, parameters/textures, and texture_assets.
4. Export PNG + sidecar files under texture_payload.
5. Write manifest with checksums.
```

### Phase 3: Payload Import Helper

```text
1. Add import_bundle_texture_payload.py or equivalent.
2. Read restore DryRun report and payload manifest.
3. Copy only textures needed by MissingTextureGuids / MissingTextureExportCandidates.
4. Write import report under the bundle.
5. Never modify .mat files.
```

### Phase 4: Verification

```text
1. Verify payload manifest integrity when present.
2. Verify no machine-local absolute paths in payload manifest/sidecars.
3. Verify payload import report is parseable when present.
```

### Phase 5: Validation

```text
1. Export a bundle with payload on a machine with original cooked data.
2. Move/copy the bundle to a test workspace without mounted game data.
3. Run material restore DryRun against a Unity project missing textures.
4. Import payload textures.
5. Let Unity generate .meta files.
6. Re-run DryRun and confirm MissingTextureGuids decreases or reaches zero.
```

## Acceptance Criteria

```text
1. Default bundles remain lightweight and do not contain decoded texture images.
2. Explicit payload export creates texture_payload/manifest.json and image files.
3. Payload manifest is portable and has no local absolute paths.
4. Downstream users without original game data can recover missing Unity textures from payload.
5. Material restore DryRun remains required before payload import.
6. Apply still requires explicit Apply and never happens during payload export/import.
7. Fresh Agents can tell whether a bundle has image payload by checking texture_payload/manifest.json.
8. If no payload and no original game data exists, the Agent reports a clear blocker instead of writing ad hoc extraction scripts.
```
